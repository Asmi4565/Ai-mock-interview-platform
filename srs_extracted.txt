1. Introduction
1.1 Purpose
This document defines the proposed functional and non-functional requirements for an AI Mock Interview Platform that helps college students and fresh graduates practise job interviews, receive structured feedback on their answers, retry weak answers, and review progress across practice sessions. It is intended to guide design, implementation, testing, and project evaluation.
1.2 Scope
The system will provide a web-based interview practice experience. A student selects a target role and interview type, answers questions in a text-based session, receives AI-assisted feedback against a defined rubric, and can review previous sessions. The first version focuses on text input to keep the project feasible for a college mini-project.
In scope: user registration and login; student profile; role and interview-type selection; question sessions; text answers; AI-assisted evaluation; feedback reports; retry practice; session history; basic progress dashboard.
Out of scope for Version 1: real-time voice/video interviews; facial-expression or emotion scoring; automated hiring decisions; resume parsing; recruiter accounts; live job listings; guarantees about employability; plagiarism detection.
AI feedback is advisory and may be inaccurate. The system must communicate that scores are practice guidance, not an objective measure of a candidate's ability.
1.3 Intended Users
Student: creates a profile, practises interviews, reviews feedback, and tracks practice history.
Administrator (optional for the first implementation): manages curated question categories and reviews basic platform content.
Project maintainer: configures the application, API credentials, and operational settings.

2. Overall Description
2.1 Product Perspective
The application is a standalone web application with a React frontend, a Node.js/Express backend, a MongoDB database, and an optional external AI API. The browser communicates with the backend through HTTPS APIs. The backend handles authentication, persistence, validation, and AI-service calls. AI API credentials must remain on the server.
2.2 Product Functions
Create an account, log in, and log out.
Maintain a student profile with target role, skills, education level, and optional project descriptions.
Select an interview category such as HR/behavioral, technical fundamentals, or role-specific practice.
Start a session and receive questions from a curated question bank and/or an AI service.
Submit text answers and move through the session question by question.
Receive structured feedback with strengths, improvement areas, and a suggested answer approach.
Retry a question or start another session.
Review previous sessions and view simple progress summaries.
2.3 Operating Environment
Client: modern desktop or mobile browser.
Frontend: React with HTML, CSS, and JavaScript.
Backend: Node.js and Express.js.
Database: MongoDB.
AI integration: external language-model API, if available and approved; otherwise the application may run in demo mode with curated questions and sample feedback.
Development tools may include Git, npm, Postman, and a code editor.
2.4 Constraints
The project must be implementable within a college mini-project timeline.
External AI usage may have quotas, rate limits, latency, or cost; the system must handle service failures gracefully.
The first version will evaluate text answers only.
The quality of AI feedback depends on the model, prompt design, rubric, and input quality.
The platform must not expose API secrets in frontend code or public repositories.
2.5 Assumptions and Dependencies
Users have internet access and a supported browser.
The development team can access MongoDB and, if required, an AI API.
Students will enter accurate profile details and answer honestly.
The team will use a limited, curated set of question categories for the MVP.
The initial release is a learning and practice aid, not a certified assessment product.

5. Non-Functional Requirements
ID
Category
Requirement
NFR-01 Performance
For typical requests under normal project-demo load, common pages and database-backed actions should respond within 3 seconds, excluding external AI response time.
NFR-02 AI response
The interface shall indicate that evaluation is in progress and shall handle slow or failed AI responses without losing submitted answers.
NFR-03 Security
Passwords must be stored as secure hashes; authentication secrets and AI API keys must not be exposed in client-side code.
NFR-04 Authorization
Backend endpoints must enforce ownership checks for profiles, sessions, answers, and reports.
NFR-05 Privacy
The application shall collect only data required for the service, explain AI-provider data sharing, and avoid requesting sensitive personal information.
NFR-06 Reliability
A temporary AI or network failure must not corrupt previously saved sessions or silently discard an answer.
NFR-07 Usability
The primary interview workflow should be understandable to a first-time student, with clear progress indicators and readable feedback.
NFR-08 Accessibility
Forms shall have labels, keyboard-operable controls, sufficient contrast, and visible validation messages.
NFR-09 Maintainability
Frontend components, backend routes, data models, and AI integration code should be separated into understandable modules.
NFR-10 Compatibility
The application should work in current versions of major desktop browsers and use a responsive layout for mobile browsers.
NFR-11 Scalability
The architecture should permit additional question categories and user accounts without requiring a complete redesign; production-scale capacity is not guaranteed by the MVP.
NFR-12 Transparency
The interface shall state that AI feedback may be wrong or incomplete and must not be treated as a hiring decision.
6. External Interface Requirements
6.1 User Interface
Landing page: purpose, supported interview types, limitations, and sign-in/register actions.
Dashboard: start practice, recent sessions, upcoming practice goals, and progress summary.
Profile page: education level, target role, skills, and optional project details.

Interview page: question text, answer editor, progress indicator, submit, and next-question controls.

6.2 Software Interfaces
Frontend-to-backend communication through JSON REST endpoints over HTTPS in deployment.
MongoDB accessed only by the backend.
AI provider accessed only by the backend using a server-side secret stored in environment configuration.

7.2 Data Rules
Every student-owned record must be associated with a user ID.
The backend must check ownership before reading, updating, or deleting student records.
Do not store passwords in plain text.
Avoid storing unnecessary personal information in AI prompts.
If AI feedback is stored, record its creation time and enough context to explain which answer it evaluates.
Define a retention and deletion approach for answers and profile data before public deployment.
8. AI Evaluation Requirements
8.1 Evaluation Rubric
Criterion
Description
Relevance
Does the answer address the question asked?
Clarity and structure
Is the explanation understandable and logically organized?
Completeness
Does the answer cover the main points expected for the question?
Technical correctness
For technical questions, are the core concepts and claims correct to the extent the system can assess them?
Examples and reasoning
Does the answer include useful examples, reasoning, or evidence when appropriate?
8.2 AI Output Handling
Request a structured response from the AI provider and validate it on the backend before saving.
Do not rely on free-form AI text as the sole source of application control or database commands.
If the model returns an incomplete or invalid response, show a retry option and preserve the user's answer.
Feedback should be respectful, specific, and actionable; it should not make unsupported claims about personality, intelligence, accent, appearance, or employability.
The model may produce inaccurate or inconsistent assessments. The UI must communicate this limitation.
Use curated questions and sample evaluation data for development and testing when the external AI service is unavailable.

10. Acceptance Criteria
A new student can register, log in, and log out.
A student can create and update a profile and start a session with supported options.
The system displays questions one at a time and saves answers to the correct session.
A completed answer can receive rubric-based feedback when the AI service is available.
An AI-service failure does not erase the submitted answer and produces a clear error/retry path.
Students can view their own session history and cannot access another student's records by changing an ID in a request.
The dashboard displays session summaries based on persisted data rather than hard-coded demo values.
The application explains that AI feedback is advisory and may be inaccurate.
AI credentials are kept in server-side environment variables and are not present in frontend bundles or source control.
Core flows are tested with valid input, invalid input, unauthenticated requests, and simulated AI-service failures.
11. Testing Strategy
Unit tests: input validation, rubric-output parsing, and helper functions.
API tests: registration/login, profile updates, session creation, answer saving, ownership checks, and deletion.
Integration tests: complete interview workflow from session creation to feedback storage.
Failure tests: AI timeout, invalid AI response, database error, and network interruption.
Security tests: password hashing, protected routes, resource ownership, request validation, and secret handling.
Usability tests: ask a small number of students to complete an interview and identify confusing steps.
Manual acceptance testing: verify the criteria in Section 10 before project demonstration.
12. Risks and Mitigations
Risk
Impact
Mitigation
AI feedback is inaccurate
Students may learn incorrect concepts or trust a misleading score.
Use a rubric, explain uncertainty, provide curated references where possible, and allow users to flag feedback.
AI API cost or quota limits
Interview evaluation may become unavailable.
Set usage limits, handle failures, use curated questions, and provide a demo mode.
Scope becomes too large
The project may remain unfinished.
Deliver text-only interviews first; defer voice, video, resume parsing, and advanced analytics.
Privacy exposure
Student answers or profile data may be disclosed.
Minimize data collection, protect endpoints, keep secrets server-side, and disclose external AI processing.
Weak user demand
Students may not use the app after evaluation.
Validate with student interviews and usability tests before adding advanced features.
Misleading numerical scores
Students may interpret scores as objective hiring predictions.
Explain scoring criteria and label scores as approximate practice feedback.

Appendix A — Proposed MVP Boundary
The minimum viable release should include authentication, a student profile, a small curated question bank, text-based interview sessions, saved answers, structured AI feedback, retry practice, and session history. The dashboard can show simple summaries. Real-time voice/video, facial analysis, recruiter portals, and automated job matching should remain out of scope unless the core system is complete and there is a clear reason to add them.
Appendix B — Important Product Disclaimer
The platform is intended for interview practice and educational feedback only. AI-generated feedback can be incorrect, incomplete, or inconsistent. Scores are not validated measures of employability and must not be used as the sole basis for hiring, admissions, or other high-impact decisions.
